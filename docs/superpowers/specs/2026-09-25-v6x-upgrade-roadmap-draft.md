# AiCommander 6.x 升级路线图草案

## 从 v5.4.0-stable 到 v6.4.0-stable

编制日期：2026-09-25。性质：基于当前代码与发布材料形成的待确认设计，不代表已经实施，也不授予自动部署、GitHub 发布或业务数据修改权限。

## 一、总体定位

**5.x 把案件、设施、地图和成果连起来；6.x 要进一步认清业务对象、理解案件过程、利用当时条件，并解释每次研判为什么发生变化。**

本路线图覆盖整个 6.x 系列，建议五个独立可部署节点，最后收口为 `v6.4.0-stable`。不为了凑版本增加页面或 Agent，不把配置模型、补齐台账或换一个界面名称当作新业务功能。

优先级仍为：日常可用、业务实用、智能化、真实竞赛展示。日常用户仍以正常录入、查看依据和判断候选为主，不管理后台任务，不逐项选择供 Agent 使用的数据。

### 当前基线与真实增量

| v5.4 已有基础 | 6.x 应做的增量 |
|---|---|
| 案件自动画像、事件片段及原文引用 | 理清不同片段的先后、同一事件、转移描述及矛盾，不只多抽几个字段 |
| 来源内稳定设施 ID、综合档案、来源版本 | 同一设施跨台账对应、案件中的设施角色、按案发时刻选择有效生产资料 |
| 最多 8 步/120 秒的动态工具循环 | 将现有设施档案、区域对照及受控后台道路计算接入助手，不重新建设 Harness |
| 道路参与设施候选召回与排序 | 在有依据的端点之间比较生产、时间、车型和多段通道条件，缺中间证据不拼完整链 |
| Outbox、后台处理、专题定时刷新、设施保守巡检 | 记录依赖、合并重复任务、解释影响范围，只提示有实质意义的变化 |
| 冻结专题及 Word/PDF 导出 | 将同一批成果编排成可以直接使用的一页简报、必要附表和有依据的关注建议 |

不重建案件库、地图库、报告中心、向量库或图数据库，不增加质疑、复核、多 Agent 辩论网络。

## 二、五个版本一览

| 版本 | 定位 | 用户能够感受到的变化 |
|---|---|---|
| v6.0.0-stable | 业务对象与历史条件统一 | 不同台账里的同一口井能够对应起来，历史案件不再只拿当前生产资料比较 |
| v6.1.0-stable | 案件过程理解与贯通式助手 | 能回答案件经过中的具体问题，并自动调用已有案件、设施、区域和道路能力 |
| v6.2.0-stable | 有证据约束的过程研判 | 在已知地点和时间条件下比较来源、转移与囤储线索，清楚展示哪段有依据、哪段未知 |
| v6.3.0-stable | 资料变化追踪与自动续算 | 新资料进来后自动更新受影响成果，明确告诉用户哪些判断变了、为什么变 |
| v6.4.0-stable | 实务材料与区域关注建议 | 直接形成案件、设施和周月材料，解释变化，最多给出三项有依据的关注内容 |

不设固定日期强行发布。6.0 先确定统一引用与依赖契约，6.1/6.2 在形成成果时记录依赖，6.3 才启用变化驱动续算，避免后期返工。

## 三、逐版本建设

### v6.0：业务对象与历史条件统一

#### 解决什么

目前同名设施不再误合并，但同一口井来自生产台账、人工点位和历史记录时，仍可能长期作为几个独立对象存在。已有版本快照，也不等于已经能从中恢复案发时适用的生产条件。

#### 升级内容

1. **一个设施、多个来源编号及历史名称。** 保留各来源原记录，增加版本化对应关系，不物理合并或删除原始点位。同名、相邻仅用于提出待核候选；唯一稳定编号或已批准映射可以自动复用。管理员只处理首次对应与冲突。
2. **案件与设施按角色对应。** 区分案发地点、被损设施、查获地点、原文提及、来源候选和人工确认关联。无需为了关联案件和设施再人为创建一条事件。明确编号且唯一匹配可形成带出处的派生链接，不自动确认实际盗取来源。
3. **生产条件按有效时段读取。** 区分业务有效时间和系统记录时间。允许后来补录历史台账，同时分别展示“按现在补齐的资料回看”和“当时系统已掌握的资料”。数据更新时间不能自动充当业务有效期。
4. **一次导入只更新发生变化的记录。** 继续复用现有导入模板、来源和幂等机制，增加新增、更新、冲突、失效的差异回执；“本次未出现”不自动等于停产或删除。
5. **建立统一依据引用。** 从本版起记录对象 ID、原始来源版本、有效时间、记录时间、画像/算法/授权版本；为后续变化追踪留下真实依赖。

#### 如何做

- 扩展现有 `JurisdictionAsset`、`MapFeatureClaim`、设施版本和案件画像；仅在确有需要时增加轻量跨源对应表，不另建资产主库。
- 对应关系可以撤销、修订，历史成果仍绑定当时采用的对应版本；读取继续核验当前权限。
- 一个来源指向多个对象、资料有效期交叠、编号复用时显式冲突，不用模型自行选一个“真值”。
- 历史缺失保留未知，不用最新值倒填过去。

#### 验收

- 同一设施不同来源可归到同一档案；同名不同设施仍独立。
- 同一历史案件更换适用台账版本后，能够解释比较结果变化。
- 只有原文提及，不会显示成已确认涉案；原始记录不被覆盖。
- 跨范围对应及历史资料读取不得泄露未授权内容。

### v6.1：案件过程理解与贯通式助手

#### 解决什么

5.1 已能抽取带出处的事件片段，当前助手也已有动态工具循环。新增价值应是理解片段之间的关系，以及实际调用已经建好的业务能力，而不是再次包装模型接入。

#### 升级内容

1. **从事件片段到可核对的案件过程。** 表达明确先后关系、同一事件的不同描述、原文记载的装载/转移行为，以及相互矛盾的说法。关系也必须引用原文，不只节点有引用。
2. **保留模糊时间与地点。** “前日晚间”“附近某站”等保留区间或候选；缺参照时间不强行换算，模糊地名不生成精确坐标。
3. **助手贯通 v5.4。** 增加设施档案、历史有效条件、区域对照工具。对于新道路问题，向既有道路后台提交有范围和预算的分析请求，再读取结果，不允许模型直接访问路由服务或传忽略限制参数。
4. **复用已有成果再补查。** 来源和版本相容时先用已有画像、历史检索、道路附件和专题；缺什么才查什么，已经回答的问题不默认重跑全套。
5. **只提示最有用的缺项。** 每次最多三项，说明该信息缺失阻断哪种比较、是否已有台账可以自动找到。找不到就保留缺口，不额外制造必办事项。
6. **收敛旧检索入口。** 普通路径统一采用授权全库检索；旧“最近 500 起”兼容入口明确范围或转调统一服务。历史报告与旧链接保留。

#### 如何做

- 案件过程关系扩展现有画像结构；规则与内网模型提取仍分层，模型关系是带来源的提取候选，不自动成为正式案情。
- 扩展 `intelligent_query_tools.py` 的白名单，不替换现有查询运行循环或引入多智能体网络。
- 交互预算继续默认 8 步/120 秒；大规模道路计算异步执行，支持取消、部分完成和后续读取。
- 模型与本地嵌入复用现有登记和离线适配。管理员配置/依赖检查是贯穿各版的落地工作，不单独占一个业务版本。

#### 验收

- 同一案情能回答“哪次装载在先、哪项转移有原文支持”等片段检索以前不能直接回答的问题。
- 否定、推测与相互矛盾的描述不变成肯定事实；模型提取不得自行获得业务确认状态。
- 同一问题因证据缺口不同而产生不同、可解释的工具轨迹；不重复发起已有有效计算。
- 原文中的指令不能控制工具；追问、道路任务及历史资料均不扩大权限。
- 未接通真实模型时标明过程理解/动态规划未启用，不把模拟模型或当前聊天模型当系统验收。

### v6.2：有证据约束的过程研判

#### 解决什么

5.2 已能比较生产设施的道路条件。下一步不是再画一条路线，而是比较已记录的案件过程与生产、时间、道路条件能否相容，避免把几个各自可达的点直接拼成运输链条。

#### 升级内容

1. **来源候选进一步使用历史条件。** 在已有道路排序上使用案发时有效的生产属性、油品及明确记录的测量条件；当前值、过期值和未知值分开。
2. **区分三类关系。** 原文记载的转移关系、已知条件下的参考通道、缺证据的中间段分别表示。道路可达不是实际经过，链条条件相容也不是正式串并案依据。
3. **有限多段比较。** 仅在已有案件、设施或已确认经验提供端点/区域线索时，比较来源至已记录查获或转移地点等必要路段。没有中间地点，不补造囤储点来凑完整过程。
4. **时间、车型及通行条件共同限制。** 只有已记录或明确标注的假设才能用于计算；硬限制先执行。时间不确定时显示条件化结果，不假装精确还原案发经过。
5. **囤储和活动区域召回提高依据门槛。** 村屯、居民点、路口或空间邻近本身不足以产生囤储候选；必须有可引用的案件线索或适用经验作为检索依据，并披露差异。只输出区域级候选，不推断具体住址、个人身份或未经证实的设施涉案事实。
6. **展示最多三项实质候选。** 后台预算内比较可以多于三个对象；展示召回范围、已完成比例和缺口，不宣称全域最优或准确概率。

#### 如何做

- 继续使用 PostGIS、现有 Valhalla 和版本化评分器，不再增加路由引擎。
- 在现有候选成果中增加过程段、约束结果、支持/反向证据及未连接状态，不另建一套案件关系主库。
- 区域模糊位置不可拿中心点冒充真实端点。没有可信入口，停止该段计算或明确只到可信公共道路端点。
- 旧算法保留用于历史读取和固定输入对照；旧版仅依赖聚落/距离的结果不升级成新算法的强依据。

#### 验收

覆盖有完整记载、只有部分段、时间矛盾、无中间地点、未知入口及道路失败六类输入。无依据时允许零候选；同一路段受相同许可和车型限制。每项条件结论均可追溯到原始来源或明确假设，不能把多段可达表述成真实运输路线。

### v6.3：资料变化追踪与自动续算

#### 解决什么

目前专题定期全量检查，设施目录保守巡检，部分区域/档案读取重新扫描全部历史。数据增加后既会重复计算，也难以直观解释“为什么这次结果不一样”。

#### 升级内容

1. 新案件、画像、台账对应、有效期、地图和已核验道路资料变化后，定位可能受影响的成果。
2. 合并连续修改产生的重复任务，同输入同版本只计算一次；交互读取与重计算分离。
3. 形成“新增依据 → 受影响条件 → 候选/材料差异”的变化记录；区分新增事实、资料补录、权限变化和算法升级。
4. 日常页面只显示实质变化：候选增加/撤回、排序有意义变化、关键依据过期、资料补齐后可计算。不把每次后台完成都变成待办。
5. 保留用户正在阅读的旧成果；明确旧版/待更新，新版可比较，不自动覆盖人工文字或已确认结论。
6. 改善区域/设施读取性能：复用当前仍有效的派生索引或片段，再执行当前授权检查；撤权立即失效，不等待后台重算。

#### 如何做

- 复用现有 Outbox、任务队列、运行事件和版本对象；新增最小依赖索引及变化记录，不建设通用工作流平台。
- 6.0 起记录来源契约，6.1/6.2 起写入依赖，本版启用调度与差异呈现。
- 新增道路可能形成捷径，影响范围不仅是旧路径经过的道路；同时考虑连接区域和候选召回范围。
- 不知道可靠依赖范围时记录“保守重算”，继续保留周期巡检兜底，不能声称精准增量。
- 限制任务并发、批次、重试与时限，不把计算移回案件保存事务。

#### 验收

- 更改一条资料能够解释哪些成果变化、哪些结果被复用；短时反复修改合并处理。
- 队列中断后恢复，案件保存不丢失；取消、过期任务不覆盖新结果。
- 撤权后旧缓存立即不能读取；无实质变化不新增用户待办。
- 用固定规模及两倍合成集对比当前方案的请求耗时、重复计算量和保存 P95，记录完整环境，不用小样本宣称生产吞吐。

### v6.4：实务材料与区域关注建议

#### 解决什么

现有报告已经可导出，但材料组织仍偏数据表；态势建议多依赖固定增量规则。最后一版应交付直接可用的工作材料，而不是把反馈、评测或比赛包装独占一个版本。

#### 升级内容

1. **变化解释。** 分开说明新发生案件、历史补录、数据修订、手法构成、设施资料和可用覆盖变化；给出可核对的分项贡献。相关性不写成原因，资料变化不直接等于实际开通/停产/封路。
2. **一页主文＋必要附表。** 提供案件研判单、设施情况单、周/月分析三类模板，正文回答“发生了什么、依据是什么、不同情况是什么、哪些仍未知、建议关注什么”。
3. **已有成果直接成文。** 页面、地图、数字和导出绑定同一冻结成果，不为每种模板重新分析。人工修改与引用分层，资料更新只提示失效和可更新段落，不覆盖人工写作。
4. **最多三项条件化关注建议。** 综合经过校验的案件变化、生产条件、道路及既有技防摘要；说明适用区域、时段、资源假设、依据、有效期和不足。无实质依据不生成套话。
5. **沿用已有方案比较。** 确有资源和覆盖资料时才复用现有空间覆盖/道路比较；缺资源不虚构方案，名义覆盖改善不等于证明防控效果提升。
6. **同一口径进入大屏。** 大屏只读取同一成果和变化摘要，不再建立独立评分或统计算法。普通用户不用新增一个材料中心。

#### 验收

- 一份冻结输入在页面、地图、Word/PDF 中引用和统计一致，复用导出不触发模型/道路重算。
- 补录旧案不会被表述成本期新增发案；资料补齐和实际事件变化能够分别说明。
- 人工编辑不被后台覆盖；来源失效或撤权时明确阻止继续引用受限信息。
- 建议不超过三项，缺依据时可以为空，不自动创建巡逻、调查、抓捕或处置任务。

## 四、共用架构与能力边界

仍保留四项业务智能体能力与确定性编排器。业务推理集中在现有查询循环和案件处理链中；查询、统计、历史解析、道路约束及评分由确定性服务完成，模型不能改写证据或替代权限判断。

新增的最小数据能力按需落在以下位置：

- 跨来源设施对应与有效期：扩展现有设施/来源/版本对象，必要时增加对应关系表。
- 案件过程和对象角色：扩展画像结构，不另造案件表或自动写正式关系。
- 条件约束和过程段：扩展候选成果，保留原评分器及冻结输入。
- 依赖及变化：轻量依赖索引、变化记录，复用 Outbox 和已有任务状态。
- 业务材料：复用现有报告与文档导出，正文编辑层不改冻结依据。

每个结果统一绑定来源版本、适用时间、分析时间、算法/模型版本、权限范围及计算完成度。权限受限、资料缺失、未知、过期、计算失败、确认不满足是不同状态，不互相代替。

数据范围默认仍是现有案件、地图、Excel 生产台账、事件、已确认经验及已有技防摘要。本草案不自动扩大到新外部业务系统、OCR 扫描、音视频、车牌原始事件或人员画像。需要新增时另行明确数据来源、权限与成本。

原始案情、人员信息、精确生产位置和内部映射不外发。兼容 OpenAI 协议不代表绑定 OpenAI 服务商；继续支持受控内网模型，不要求更换框架。模型未启用时确定性能力继续工作。

## 五、实施与发布规则

### 先做一次简短基线盘点，不单独发版

实施开始时核实真实数据形态、现有服务配置与模块状态，形成“规则可用、模型未启用、缺资料、待现场确认”清单。尤其确认同井跨台账对应、案件原文过程信息、设施入口与生产有效期能支撑到哪一步；未知写未知，不要求全厂资料收齐再动工。

### 验证安排

- 开发中只验证受影响模块；每版收口执行一次核心回归和本版端到端业务路径。
- 权限、映射、时间有效期、路由约束、迁移、续算分别补对应高风险检查。未改地图源/路由引擎/构建依赖，不重复下载、制图或编译。
- 真实模型功能至少用一个实际配置模型验证真实请求、引用、否定及工具调用，再宣称该功能已启用。模拟响应和当前聊天模型仅能辅助开发。
- 模型或现场条件不足，不阻塞独立的确定性功能；能力清单明确延期，不把“接口写完”计为模型效果交付。
- 源码、隔离组件、目标服务器、真实业务效果分开记录。维持不把 30 天试用、固定真实样本数或全厂道路收齐设为源码 Stable 门槛。
- 核心保存不等待智能分析；沿用冻结环境下案件保存 P95 相对基线退化不超过 5% 的目标，现场性能独立记录。

### 发布与回退

路线图确认并授权实施后，每个 `v6.x.0-stable` 完成自身门槛，统一更新一次 GitHub，附发布说明、迁移、验收和回退材料。普通修正随版本积累；生产阻断或高危安全问题才单独 hotfix。

保留 `v5.4.0-stable` 为系列基线，之后每版保留上一 Stable。映射及派生数据升级使用增量迁移；恢复旧版连接独立兼容备份，保护升级后新增原始案件、事件和生产资料。

## 六、竞赛展示与最终效果

展示不另造算法，直接用日常流程的五个可观察变化：

1. 同一设施在两张台账使用不同名称，系统按受控对应展示同一对象，保留来源差异。
2. 一次案件录入形成带出处的过程描述；模型不能补造原文没有的中间环节。
3. 切换案发时适用的生产或道路条件，候选变化，并指出具体哪条依据起了作用。
4. 新增一条可靠资料，只更新受影响结果；没有可靠影响范围时明确显示保守重算。
5. 同一批成果直接形成一页材料；缺证据时保留未知，断网或模型故障时核心录入和离线地图仍可使用。

**v6.4 的目标不是“系统生成更多结论”，而是“同一份数据能被正确理解，每条判断有适用条件，每次变化有原因，成果能直接用于日常工作”。**
