# AiCommander 未投产阶段：全面业务重构与能力升级建议

日期：2026-09-27。审查基线：当前 `6.0.0-stable` 源码工作区。

**2026-09-30 状态：用户已授权推进至 v6.5 并统一发布 GitHub。** v6.1—v6.3 的资料、生产对象、案件过程/检索/条件底座继续保留；R11—R12、R08 完整统计续跑及 R10 统一材料已接入并完成本地功能收口，见 [v6.5 发布说明](../../releases/v6.5.0-stable.md)和[综合验证](../../validation/2026-09-30-v65-implementation.md)。实际远端发布在该记录单列，不以规划或版本号代替；真实模型、目标服务器及正式业务效果未计为完成。以下为原审查依据，版本交付按本文件末尾的调整后节点执行。未清空现用数据库或重制地图。

## 一、结论：现在适合进行一次有边界的深度重构

建议从“为旧模块增加适配器”转为“围绕业务对象重新组织实现”。**保留已经有价值的能力，不保留没有业务价值的历史结构。**

可直接调整表结构、内部接口、状态名称、页面组织、后台任务协议；不必长期双读双写、保留所有旧 URL、迁移无价值的派生缓存。退出旧模块应真正从正式运行包移除，而不是永远藏在高级菜单或返回 410。

但没有生产旧数据，不等于没有需要保护的内容：两市公共地图包、路网原始数据、生产 Excel、坐标模板、人工核验点位、模型配置和有用的演示样本仍须核定。本次没有读取数据库确认这些内容的数量，也没有据用户这句话推定可以直接清空任何目录或数据库。

| 路线 | 判断 |
| --- | --- |
| 继续逐层兼容 | 改动小，但会把多种案件字段、多个成果入口和旧状态长期带入正式部署；不作为主方案 |
| 全仓推倒重写、换框架 | 会重复建设离线地图、路由、权限、导入和恢复能力；收益不足，不建议 |
| **目标模型重构＋按业务链切换** | **推荐。** 新建干净目标结构，同版切换前后端和后台消费者；复用已验证的地图、计算、导出与安全组件 |

6.0 刚完成的统一读取、组合成果、来源失效、后台链条、版本确认和开关分离继续保留。它们是重构的可靠基础，不是需要再做一次的新增功能。

## 二、审查范围与证据边界

本轮沿主要消费者检查：录入/导入、事件与线索、质检、画像、人员车辆与油品记录、生产地图与道路、历史检索、候选、专题、助手、工作台、会议、结论/经验/报告、权限上下文与后台事件。

- 核对当前源码及现有审查材料，未将旧 v5.4 问题直接当成 v6.0 现状。
- 这是业务与结构审查，不是全仓逐行安全审计；下面的结构风险不等于已经发生过数据错误或越权。
- 未启动服务、访问实际业务库、运行模型、下载地图或重复跑回归。源码有实现不代表实际模型已启用或正式业务效果已验证。
- 历史“主系统只有单次 LLM 调用”的判断已不适用：当前助手已有受控多步循环；旧单次 executor 已退役。

## 三、建议直接重构的 14 条业务链

优先级表示依赖和业务收益，不表示每项均是已复现故障。P0 应在首次正式导入前解决；P1 是新主流程；P2 可在该基础上深化。

### R01 / P0：案件、事件和线索统一采集，保留不同业务身份

现状：案件与事件有各自的时间、地点、车辆和油量；事件通过单个 `related_case_id` 关联案件。案件还有独立 CaseTip。事件转案件的实现先创建案件，再回写事件关联，存在两段提交。

目标：**统一采集入口，不把所有记录强塞进一张案件表。** 原始记录作为来源，案件档案、独立事件和未核实线索保留各自类型；通过显式关联表达“由此记录建案”“补充此案”“同源展示”。

- 用户先记录已知内容；不知道准确时间、地点或性质时可以保存草稿/发现记录，不强填假值。
- 转为案件是一次原子业务操作，带稳定来源 ID 和幂等键，不复制出两份互不关联的事实。
- 同源事件不再重复计为另一起案件，独立事件继续独立统计。
- Excel 更正、补录只生成来源修订；相似文本不自动认定同案，可靠来源编号或人工对应才可合并。

依据：`models/event.py:88`、`:103`、`:124`；`api/events.py:524`；`services/case_import_batch_service.py:13`。

### R02 / P0：重设时间、地点、数量三个最基础的数据契约

当前案件只有一个必填 `occurred_time` 和一组主坐标；`oil_volume` 本身没有单位字段，注释依赖“吨/升按约定”，事件是升，回收记录是吨。不能仅靠界面默认值和注释支撑跨来源统计。

建议分别建立有类型的值：

| 维度 | 新契约 | 业务收益 |
| --- | --- | --- |
| 时间 | 发生区间、发现时间、报送时间、录入时间、时区、精度和原文 | “昨晚”“某月”“发现时”不冒充精确案发时刻；统计显示不确定范围 |
| 地点 | 角色、原文、点/线/面、精度、来源、设施对应 | 案发地、查获地、原文提及、候选来源、临时保管地不共用一个点 |
| 油品测量 | 数值、单位、测量对象/环节、方法、时间、含水率口径及来源 | 涉案量、查获量、移交量和回收量不直接相加，也不混用车辆总重 |

有充分参数才做确定性单位转换；缺密度、测量条件或分数口径时不推导吨升换算或净油量。坐标候选未核实仍保留区域，不能以区域中心点作为精确道路端点。

依据：`models/case.py:29`、`:41`、`:62`、`OilRecoveryRecord`；`models/event.py:104`；`services/case_road_vehicle.py:9`。

### R03 / P0：一套实体明细，不再同时维护 JSON 和子表

案件同时保存 `involved_persons/vehicle_info` 和 `CasePerson/CaseVehicle` 子表；旧质检仍从两处读取并相加计数。未来直接指定一个正式明细来源。

- 原始导入内容保存在来源修订里；正式人员、车辆、油品批次使用有类型的明细及案件角色关联。
- 原文提及与已录入对象不是同一层，不因同名或同车型自动合并。
- `features` 不再继续作为人工标签、旧模型摘要、经验卡和分析标记的通用容器。
- 标签、提取候选、计算结果分别写派生层；人工判断引用对应来源/结果版本。

依据：`models/case.py:36`、`:48`、`:73`、`:77`；`services/case_quality_service.py:150`、`:329`。

### R04 / P0：重新设计缺项判断，不再用一个百分制分数代表所有问题

当前质检把资料完整、车辆材料、时效和研判条件加成一个分数；部分信号由词语出现判断，存在否定表述仍触发补充项的结构风险。代码还保留同伙识别、巡逻、圆桌等旧就绪条件。这不能完整代表当前业务主线。

改成三个互不替代的判断：

1. **录入有效性**：字段格式、单位、矛盾、来源；仅必要的格式错误阻止保存。
2. **资料完整性**：根据案件类别、当前阶段和适用的业务规则提示，不对所有案件套全套车辆照片清单。
3. **能力可用性**：能做历史检索、区域分析、道路比较或材料导出中的哪些部分，缺什么会影响哪项结果。

最多提示三项真正影响当前使用的缺口。已有语义极性应供质检复用；“未发现车辆”不能因为包含“车辆”就要求补牌照。报送时限等组织规则独立配置和版本化，不能以猜测的发生时间判迟报。

这不是取消已有适用的业务要求，而是把它们从“全案总评分”拆成按场景适用的规则。无经验卡、不出报告、未开模型都不应成为案件未完成。

依据：`services/case_quality_service.py:118`、`:152`、`:232`、`:267`、`:349`；实际保存前入口 `api/cases.py:380`。

### R05 / P0：统一业务对象身份与资料有效期

地图来源声明、设施、地图快照和道路是不同对象，不能全部按名称合并，也不能让同一设施在不同来源永远互不认识。

- 设施具有稳定业务 ID；台账编号、历史名称、不同来源声明指向它，映射可撤销。
- 公共地名、生产设施、技防设备和道路拓扑要素分型，显示在同一地图不代表相同业务权限或可信程度。
- 台账修订记录“业务生效时间”和“系统收到时间”；案发时有效资料与现在知道的资料可分别查询。
- 道路有稳定线段/入口/设施连接关系；导入批次不是道路身份，公共吸附点不是可信入口。

保留既有来源、坐标转换、异常隔离、PostGIS 与 Valhalla，不另建资产主库或换路由引擎。

依据：`models/map_foundation.py`、`models/jurisdiction.py`、`models/internal_roads.py`；`services/map_foundation_service.py:523`、`:604`、`:694`。

### R06 / P1：案件档案重构为真正的主工作界面

不继续在案件侧栏追加更多卡片。改成一个稳定案件档案：**概览／原始资料与补充／过程与关联／地图道路／成果与业务附件**。

- 正常录入一次即可进入自动整理；人只处理关键矛盾、候选判断或按需修改。
- 统一当前分析上下文：主体、范围、时间、资料版本、成果引用、地图选择；跳到设施/专题再返回不丢状态。
- 编辑原始记录与阅读冻结成果分开；查看不写入、导出不重新分析。
- 人员、车辆、回收、证据、奖金附件和经验采纳各就其位，不因退出旧页面而删除独有功能。

依据：`frontend/src/pages/Cases/Cases.tsx:1775`、`:1883`；`frontend/src/services/caseContext.ts:47`、`regionalContext.ts:3`。

### R07 / P1：从标签画像升级为可核对的案件过程

现有事件片段明确只是句内共现，已有肯定/否定与原文引用，但不是完整的主体、先后或来源去向关系。

建立有限结构：**动作—时间区间—对象—地点角色—油品/测量—关联事件—原文出处—表述性质**。原文没有交代的关系保持未知；模型提供候选，引用和类型校验通过也不等于已核实事实。

前端直接显示“已交代的环节、相互矛盾的记录、尚未交代的环节”，供检索、候选比较与材料共用，而不是再增加一个过程 Agent。

依据：`services/case_event_fragments.py:43`、`:91`；`services/case_local_semantic_model.py:25`。

### R08 / P1：检索从请求内扫描升级为片段级召回

现有历史检索不是只查最近 N 条，但仍按授权案例分批扫描，并在预算内计算；长文本向量采用分块平均。应把计算尽可能放在资料变更后完成。

- 索引单位包括案件关键表述、过程片段和已确认经验，统一来源版本与权限。
- 结构、词项、语义各自召回后融合；不能以关键词命中作为语义分支前提。
- 结果展示共同条件、重要差异和适用边界，不把相似度称为正确概率。
- 查找少量历史参考与全量统计使用不同执行模式；完整统计可后台续跑，部分结果明确覆盖范围。

复用 PostgreSQL/pgvector 和离线嵌入，不新建第二套向量库或知识库操作页。

依据：`services/case_history_retrieval.py:155`；`services/case_history_vector_service.py:32`；`services/local_embedding_service.py:133`。

### R09 / P1：从“分数前三项”升级为条件对照与关键缺口

6.0 已统一道路成果，下一步应深化业务含义，而不是再拼一层摘要。

- 硬排除、明确不符、资料未知、支持条件分别展示；一个总分不能掩盖不同状态。
- 根据案件时间、生产资料和可信入口形成候选集合，记录召回范围、计算预算与未完成部分。
- 展示“为何排除／为何保留／哪条新增资料改变了排序”。
- 可增加条件敏感性对照：如果补到车辆尺寸、有效油品测量或入口资料，会消除哪些具体未知。只说明依赖和条件变化，不虚构信息增益概率。
- 只有已有来源或线索支持端点时，才分析必要的转移区段；附近村屯、道路或仓房本身不能成为囤储结论。

依据：`services/facility_candidate_pool.py:129`、`scorers/facility_roads_v52.py:84`、`services/facility_production_conditions.py:24`。

### R10 / P1：统一成果、人工判断与材料，不再维护多条结论流水线

现有 Report 偏会议，KnowledgeAsset 包含经验和报告快照，另有 Conclusion、案件组合、专题快照和查询材料。它们可共用索引与阅读器，但不能把所有内容强行变成同一个无类型 JSON。

目标是：**统一成果外壳＋类型化正文＋冻结来源清单＋人工判断记录＋导出文件**。

- 案件、专题、设施、周期和可选多模型比较是不同成果类型，共用版本、权限、引用和导出契约。
- 经验仍需独立的适用条件和采纳记录；会议讨论也不等同于确定性案件事实。
- 确认、保留参考、依据不足、有依据排除等决定绑定具体版本，允许关联新增材料，不成为每案必做审批。
- 统一目录直接搜到所有成果，助手、案件页和地图打开同一个阅读器。
- 数字、对象名称、地图和证据由确定性程序装配；可选模型只组织表达，不补证据或改分。

依据：`models/report.py:6`、`models/conclusion.py:6`、`models/knowledge_asset.py:21`；`frontend/src/pages/Reports/Reports.tsx:104`；`services/intelligent_query_document.py:40`。

### R11 / P1：助手能完成业务问题，不只是显示工具卡片

当前已有 9 类受控工具、最多 8 步/120 秒的动态循环；模型被要求选择工具而不生成答案。Lab 则使用固定任务工具序列，两者不能混称同一种自主能力。

重构方向：共享工具声明、任务信封、预算、证据、取消和计量协议；保留确定性后台执行与交互模型规划两种模式。**不要求把所有 Worker 改成一种状态机，也不把实验审批工具权限交给普通助手。**

优先补齐设施档案、历史有效资料、过程证据、已有成果解释和受控派生计算工具，再提供一层证据化答案编排。没有模型时仍能用业务预设和确定性工具完成查询；界面明确当前模式。

原文和工具结果都作为资料，不能提供任意 SQL、Shell、外部网址或自动执法任务。SDK 和厂商协议不是这次重构目标。

依据：`services/intelligent_query_loop.py:23`、`:70`、`:79`；`agent_runtime/runtime.py:24`、`:89`；`services/agent_service.py:1`。

### R12 / P1：专题、工作台和变化续算围绕“问题”，不围绕流程状态

专题改成“保存并持续关注一个业务问题”，从当前案件、设施或助手带入；无需先理解词项、极性或 Agent。

例如：某区域近期同类手法是否有变化；某类油品的来源候选还缺哪些条件；某设施有哪些明确关联与历史参考。条件修订保留版本，支持固定/滚动窗口，地图、表格、图谱、报告只是同一成果的不同视图。

工作台只突出少量有意义的变化：新资料排除了候选、道路变化使原结果过期、关键缺口已补齐。后台重试、刷新但内容未变不制造待办。

后台复用 Outbox 和不可变成果，登记实际依赖、合并连续修改、拒绝过期任务回写；新道路捷径需考虑连接区域，没有可靠影响判断时标注保守重算。

依据：`services/analysis_topic_service.py:197`、`:290`；`services/road_refresh_jobs.py:1`；`services/daily_workbench_service.py:20`。

### R13 / P0：把佐证文件与引用变成稳定的来源对象

案件证据使用文件路径，事件附件使用 JSON，道路核验依据又是字符串，跨页面引用容易停留在“附一段文本”。建议共用受控证据对象和来源引用契约，而不是新增文档识别模块。

- 文件对象记录哈希、受控存储键、类型、敏感级别、采集时间，不以服务器路径作为业务身份。
- 引用可以指向某版原文的具体片段、台账某行、现有照片或道路核验记录。
- 案件、事件、设施、候选和报告引用同一对象，不复制多份附件；模型不能自己生成不存在的引用。
- 源对象撤销、失效或无权访问时明确不可用，不悄悄寻找相似材料替代。文件存在和内容真实仍是不同问题。

不扩展扫描 OCR、视频分析或外部资料接入；先让已有佐证目录和文字证据真正贯通。

依据：`models/case.py:153`、`models/event.py:121`、`models/internal_roads.py:40`、`models/case_insight.py:61`。

### R14 / P0 起步、P2 完善：事件事实与消费者执行状态分开

当前 Outbox 既记录变更又带单消费者状态，画像入队还兼顾链条和历史索引。这一实现已能工作，但未投产时可直接清理耦合，避免以后一个新下游就再加一组标志。

- 同事务写不可变业务变更：什么对象、哪个版本、何种变化、谁做的；不把“资料变更”等同于“必须跑某一个 Agent”。
- 按消费者保存投递与处理进度，画像、检索、设施投影可独立幂等、重试或停用。
- 任务及其尝试记录管理租约、取消和故障；普通用户只看到业务就绪状态。
- v6.1 先统一变更与来源标识，后续完善依赖与局部重算；不在第一版建设通用工作流引擎或全系统事件溯源平台。
- 重建索引和画像可以重放来源，不能重放人工确认来执行未知副作用，也不能清空人工决定。

依据：`models/case_pipeline.py:8`、`services/case_pipeline_service.py:126`、`:170`；`models/preprocess_job.py:6`、`models/agent_task.py:6`。

## 四、适合新增或深化的功能：收敛为六项

这些是能力包，不要求新增六个一级菜单。

| 能力 | 用户实际怎么用 | 与已有能力的差别 | 顺序 |
| --- | --- | --- | --- |
| 智能记录与关键补充 | 粘贴案情/导入表格，自动形成草稿与最多三项关键提示 | 从字段必填评分变成按业务任务判断缺口；未知也能正常留存 | 第一批 |
| 生产地图“可计算性”视图 | 管理员直接看到哪些井缺入口、路段断连、条件过期 | 不是再画底图，而是解释为什么某个分析做不了，并小批补齐 | 第一批 |
| 油品与数量条件校核 | 核对查获、移交、回收及相关车辆记录的单位、环节和矛盾 | 不只判断是否填过油量；不做缺参数的自动吨升或净量换算 | 第一批 |
| 案件过程线与候选条件对照 | 点开每一环节查看出处，比较候选的支持、不符和未知 | 不只显示标签/分数；不生成实际轨迹或具体囤油点断言 | 第二批 |
| 关键补充与情景对照 | 问“补什么最能改变当前判断”“入口关闭后有什么不同” | 复用真实规则和道路计算，场景副本不改正式台账/限制 | 第二批 |
| 持续关注与实务材料 | 保存一次问题，有实质变化再看；导出一页简报或完整材料 | 把专题、工作台、查询卡片和报告接成一条链 | 第二批 |

### 最值得用于竞赛的三项联动

1. **从一段不完整案情开始。** 系统显示有出处的过程、能运行的分析和真正有用的补充项，不要求先挑资源。
2. **补一条资料，结果出现可解释变化。** 新增可信入口、修正油量单位或补充线索后，明确哪些候选改变、哪些没有改变。
3. **同一份成果贯通案件—井场—专题—材料。** 地图和正文引用相同版本；断网、缺资料或模型停用时诚实给出部分能力。

展示复用正常业务服务和隔离合成数据，不另造演示算法，也不把任意示例当成真实业务效果。

## 六、目标数据结构：少量业务域，清楚的来源关系

下表是领域设计，不要求机械新建同名表，也不建设通用 EAV/万能关系表。

| 业务域 | 主要对象 | 保存什么，不保存什么 |
| --- | --- | --- |
| 资料来源 | 来源记录、来源修订、导入批次、出处 | 原文、单元格、提交者、时间、来源键；不混入模型判断 |
| 案件与记录 | 案件档案、独立事件/线索、关联、对象角色、测量 | 已录入的业务记录及核实状态；“记录存在”不等于现实事实已证实 |
| 地理生产 | 设施、来源身份、属性有效期、道路、入口、通行条件 | 一对象多来源、有类型几何、可追溯有效条件；不以同名自动合并 |
| 派生分析 | 画像/过程片段、检索索引、候选、计算附件、成果快照、依赖 | 可重建、绑定输入和规则；不回写原始事实 |
| 人工判断 | 针对某对象某版本的决定、理由与引用 | 保留版本审计；不自动继承到不同内容，不强制每项审批 |
| 专题与材料 | 问题/条件修订、冻结成果引用、模板、导出文件 | 复用来源，材料不再自行重做分析 |

状态至少分开：**案件办理状态、资料核实状态、分析运行状态、成果时效状态、人工判断状态**。不能用一个 `completed` 同时表达“模型执行完、报告生成、案件办结”。

授权改为显式、带类型的执行上下文：用户/服务身份、可见范围、道路许可、用途和策略版本；普通服务缺上下文应失败，后台跨范围任务须明确声明服务身份。当前依赖 Session 信息和集中 ORM 过滤的机制应保留为防线，而不是把新架构变成绕过鉴权的捷径。

## 七、推荐的未投产切换方式

1. **先做资产清单。** 分清业务原始资料、可复用地图、配置、合成演示数据、派生缓存；不因为“未投产”直接删库。
2. **保留 v6.0 源码/配置恢复点。** 明确当前未提交工作包和用户其他文件，不能整仓清理或直接覆盖。
3. **建立空的目标库与新初始化基线。** 可收拢旧增量迁移，不让新环境必须一直执行 2.x—6.0 的全部历史分支；旧迁移随恢复包归档，而不是未经验证直接删除。
4. **只搬必要来源与人工资料。** 需要保留时按映射表一次性转换和核对；不要求搬所有旧摘要、任务轨迹和缓存。没有保留需求的合成数据可重新生成，但清理具体库/文件仍须执行前核定范围。
5. **派生层重建。** 索引、画像、候选、关系投影和材料按新来源重新生成。已可用的地图包和路由构建物只验证引用兼容，不盲目重新下载/编译。
6. **按完整链路切换。** 每个领域同时修改模型、API、页面、后台任务和测试；不先换表结构，留下旧前端长时间猜兼容。
7. **删旧路径。** 消费者均已切换后移除旧表/路由/配置/测试夹具；保留规则的业务验收场景，不保留无价值的旧实现断言。

这条路线不要求线上双写、停机窗口或复杂生产数据回迁；正式部署后再改动已使用的数据契约，才按生产迁移管理。

| 节点 | 重构重点 | 当版必须有的可用成果 |
| --- | --- | --- |
| v6.1 资料与案件骨架 | R01—R04、R13、R14 最小变更契约、案件档案骨架、目标库初始化；退出旧首页/重复对象 | 一次录入、类型清楚、未知可存、油量单位明确，缺项提示合理 |

| v6.3 案件理解与候选条件 | R07—R09、片段级检索、助手相关工具 | 案件过程有出处；历史参考可比较；补充资料能改变候选依据 |

统一成果最小契约、来源版本与执行上下文必须从 v6.1 使用；不能等到 v6.5 才统一数据。v6.5 是阅读、材料和最后消费者收口，不是再加一轮包装工程。

若实际使用优先需要报告，材料模板可以随 v6.1 起分批交付，不被版本编号机械阻挡。先做目标模型和一个纵向场景，再推广，避免全仓重构一次性失去可运行版本。

## 九、验收应围绕业务问题，而非测试数量

每个工作包先针对性验证，收口再跑相关核心链，不重复下载地图、编译路由或全仓反复验证。

至少保留这些固定场景：

1. 原文说“未发现车辆”，不产生强制车辆补录；不同案件阶段不使用同一材料清单。
2. “昨晚、井场东侧”按不确定时间/区域保存，不编造精确时刻和坐标。
3. 同一发现记录转案件重复提交不重建案件，统计不重复计数。
4. 事件的升、回收的吨以及不同环节油量不直接汇总；没有参数就明确不能换算。
5. 同井异名可追溯对应、同名异井不误并；当前台账不能冒充案发时资料。
6. 较老案件的重要过程片段可召回；否定、不确定与肯定分开，索引缺失不等于无匹配。
7. 候选缺入口、被硬限制排除、道路失败分别有不同状态；更改条件能解释排名变化。
8. 补充依据产生新结果和差异说明，不覆盖旧人工判断；未变化资料不反复处理。
9. 案件、设施、专题、正文、地图使用同一成果引用；撤权后历史引用同样不能泄露。
10. 模型关闭、Redis/道路服务异常不阻断资料保存；普通用户不需要管理任务恢复。

真实模型、目标服务器与正式业务效果继续单独记录，不恢复 30 天试用或固定真实样本量作为源码发布门槛。无数据不能声称已校准命中率，无测试不能只凭新版本号称稳定。

## 十、不建议增加的内容

- 不新增质疑、复核、辩论 Agent 网络，不让用户围着多 Agent 反复确认同一份材料。
- 不建设通用巡逻调度、自动调查抓捕、自动正式串并案或人员风险画像。
- 不通过堆地图服务商、再换数据库/路由/SDK制造技术亮点。
- 不在本轮扩展扫描识别、连续视频、原始抓拍或新外部业务系统；确有需要另立数据接入范围。
- 不把“未知”改为零、不把“无记录”改为“没有”、不把“条件相似”改为实际发生。

**最终目标：资料进得来且不用假填，地图不只是能看而且知道哪里能算，分析能说明依据和缺口，材料能直接用，用户不必理解内部模块。**
