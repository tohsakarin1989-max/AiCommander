# 可选能力开关与排程迁移说明

## v6.4—v6.5 覆盖规则

以下规则优先于历史章节：

- `ENABLE_LEGACY_OPERATIONS_MODULES=true` 在所有环境均拒绝启动。旧执行型巡逻、人员、重点部位及团伙 API/页面已退出，保留历史表和原始案件资料，不提供重新开启开关。
- 旧 `410` 停用壳及结论工厂已移除；历史人工结论从统一材料阅读器读取，不恢复旧生成流水线。
- 六项确定性业务预设遵守 `ENABLE_INTELLIGENT_QUERY`，无需模型；自然语言模式仍要求可信内网配置，不因升级自动接通。
- 专题后台通过普通 Worker/Beat 续算，每 15 秒推进工作片；不依赖 Lab 或模型，取消当前刷新与暂停自动更新是不同动作。
- 后端、Worker、Beat 同步升级并先完成迁移 `v64t01 → v65r01`。来源修订触发器及 PostgreSQL 序列不能漏装；不要只部署前端。

升级/兼容恢复见 [v6.5 发布说明](releases/v6.5.0-stable.md)。下方“非生产环境可重新开启”“无迁移”等表述仅记录旧版历史，不适用于当前源码。

## v6.0 覆盖规则

以下 v6.0 规则优先于下方保留的 v5.4 历史说明。升级不会修改实际环境文件，也不会接通模型。

| ENABLE_INTELLIGENT_QUERY | 新查询 API 与 Worker/Beat | 历史读取、导出、取消 |
| --- | --- | --- |
| 未设置或留空 | 继承旧 ENABLE_AGENT_LAB=true 且 AGENT_MODE 非 off 的启用条件 | 始终重新鉴权，仅本人已授权内容 |
| false | 不创建、不领取新查询，取消每 5 秒消费排程 | 保留 |
| true | 与实验 Lab 独立开启；不解除模型原文出域限制 | 保留 |

前端从运行状态读取同一开关；状态读取失败不放开提交。既有模型 ID 只代表已选配置，不证明连通或实际效果。
仅开新查询时，生产编排也启动既有专用队列 Worker（技术 profile 名仍为 agent-lab），
并不因此开启实验工具或候选写入权限。所有进程需使用同一配置并重新创建/重启，不能只更新前端。

新增 `aicommander.queries.expire` 每 60 秒在普通队列清理过期查询：运行超过 120 秒、排队超过 24 小时，
最多一批 100 项；重复执行不重复追加失效事件。关闭 Lab/新查询不关闭该清理，也不执行任何模型或业务写入。
原历史审批清理仍走旧专用队列，不被本改动取消；停止其 Worker 时仍按下文处理。

新增 `aicommander.chain.process_pending` 每 10 秒在普通队列消费案件变更事件，处理链条派生候选；
它与案件画像、统一成果、专题等一样不依赖 Lab 或模型。后台退出/重启依靠事件租约恢复，不从保存接口同步全库扫描。

## 1. 智能查询停止空轮询

| `ENABLE_AGENT_LAB` | `AGENT_MODE` | 智能查询排程 |
| --- | --- | --- |
| `false` | `off` | 不注册每 5 秒查询消费排程 |
| `true` | `off` | 不注册每 5 秒查询消费排程 |
| `true` | `shadow` | 每 5 秒排入原 `AGENT_REDIS_QUEUE`，过期时间仍为 5 秒 |
| `true` | `assist` | 同上；写入开关和人工审批要求不变 |
| `false` | `shadow` / `assist` | 配置校验拒绝启动，不自动修正配置 |

仅取消关闭状态下的定时空查询任务。任务名称、Celery 注册、专用队列路由、普通案件治理、
画像、融合研判、统一成果、历史索引、设施摘要、已保存专题、日周简报、地图包和道路任务全部保留。

排程在 Beat **进程启动时**按配置生成，不实时读取 `.env`。修改开关后需要：

1. 让后端、Beat、普通 Worker 和专用 Agent Worker 使用同一份已批准配置。
2. 本地进程须重启相关进程，尤其是 Beat。只重启后端不会更新排程。
3. Docker Compose 中修改环境文件后，使用原有发布命令及相同 Compose 文件/覆盖文件重新创建相关服务实例；
   只执行 `docker compose restart` 不会加载新环境。启用时仍按既有 `agent-lab` profile 启动专用 Worker。
4. 验证 `/api/runtime/status` 的功能状态、`/health/agents` 以及 Beat 已加载的任务清单。不要只根据前端入口判断开关已生效。

这不是紧急撤销运行中任务的机制。已有 `queued` 或 `running` 查询记录不因关闭排程被删除或改成“成功”；
已经发到队列的任务仍保留。关闭状态的查询 Worker 不继续领取，重新开启后恢复领取并按现有规则处理失效任务。
已开始执行的 Worker 须按既有取消/停用流程处理，不能把修改配置文件视为立即中断。

## 2. 历史审批失效清理不关闭

`expire-agent-approvals` 每 900 秒的排程、任务及原专用队列路由继续保留。
即使 Agent 开关关闭，只要该队列仍有 Worker 消费，清理任务仍会把过期审批标成失效，且绝不执行候选写入。

若同时停止专用 Worker，清理消息会等待，历史审批状态可能延后更新；恢复消费后再失效。
审批执行本身仍检查启用状态、有效期和原有权限，不会因为清理延迟就允许过期写入。
本次不改队列路由，也不通过清空 Redis、删任务或删历史记录来消除待处理状态。

## 3. 旧巡逻、人员、重点部位改为显式开启

`ENABLE_LEGACY_OPERATIONS_MODULES` 的代码默认值由 `true` 改为 `false`。

- **未设置该变量的开发/测试环境**：升级并重启后不再挂载三个旧模块的 API，前端运行配置报告关闭。
- **已明确设置 `false` 的环境**：行为不变。
- **仍需查验旧流程的非生产历史环境**：管理员可明确设置 `true` 后重启后端，恢复旧 API；不需要恢复数据库或重建数据。
- **生产环境**：始终禁止 `true`，生产 Compose 也固定为 `false`，不能通过该开关绕过厂区隔离边界。

已有显式 `true` 不会被升级自动改写。部署管理员须核对该环境确实用于受控历史兼容，不能把它当作正常生产默认。
旧表、模型和业务服务继续保留，关闭只影响路由挂载和运行功能状态。回到显式开启无需数据迁移。

## 4. 验证边界

本轮验证分别覆盖默认值、有效/无效开关组合、全新进程路由与排程加载、关闭时保留在途查询记录、
过期审批清理、旧业务兼容测试及核心健康检查。测试不修改全局 `conftest` 来强制开启旧模块。
目标服务器是否重建服务实例、专用队列是否实际有人消费，仍须部署侧分别核实。
