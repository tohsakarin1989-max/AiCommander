- 候选：测量开始时冻结当前 `backend/app`，包括本轮未提交改动；不在测量中读取变化中的源码。
- 复用原保存基准的认证 ASGI 调用、隔离文件 SQLite，以及 v6.2 的 200 条历史案 / 10 次预热 / 50 次正式样本规格。
- 三组各三轮，交错运行：基线不带提交标识；候选每次携带全新 `Idempotency-Key`；候选不带标识作诊断对照。
- 每个 POST 都必须产生独立新案件和自动编号，随后对该案执行一次原有 PUT 编辑。没有重放请求。

- 三组使用完全相同的 SQL 计数 / 游标计时观察器。游标耗时不包括事务提交、文件同步和 Python 运算，不等于完整数据库成本。
- 禁止网络连接、外部模型；不接现用数据库。

## 已定位开销与最小优化

- 原带标识新增固定执行 55 条 SQL，旧路径 51 条。多出的回执 `SAVEPOINT / INSERT / RELEASE / UPDATE` 各一条是确定的新增成本。
- 改为 SQLite / PostgreSQL 原生 `INSERT ... ON CONFLICT (user_id, idempotency_key) DO NOTHING RETURNING id` 认领，同事务中保留绑定案件的 UPDATE。因此少执行两个保存点语句，新增实测降为 **53 条**。没有提前提交，也没有缓存授权结果或返回旧响应正文。
- 只有指定的用户 + 标识唯一冲突可忽略；外键、非空和其他约束错误仍抛出并回滚。摘要不一致仍冲突；重试仍读取当前可见案件、核验写权限；删除案件不释放回执。SQLite 仍先取得 `BEGIN IMMEDIATE`，自动编号的原保存点保留。
- 无标识保存与 HEAD 对照仍为 51 条 SQL，编辑仍为 48 条；案件服务、数据库授权和请求认证业务链未增加查询。可选请求头解析 / 空分支及路由、模型注册属于本轮代码差异；新建用户的范围配置不在案件保存调用链上。不能把诊断组全部 P95 差异归于这些微小差异。
- 对首轮冻结候选无标识另做一次运行时诊断，**不加入任何门槛分布**：第 53 个新增请求耗时 114.568 ms，其中 Python 第 2 代垃圾回收耗时 **90.809 ms**，回收 2800 个对象、无不可回收对象。这确认了各组约 115 ms 级共同长尾的一项来源，但不能解释所有 25–56 ms 级 P95 波动。未禁用、强制提前触发或调整 GC 阈值。

回归证据：

- SQLite 提交与迁移窄回归：**16 passed**。减少保存点用例先失败，优化后通过；保留失败提交、丢响应、内容冲突、权限变更、删案、自动 / 手工编号并发验证。
- 实际 PostgreSQL：**1 passed**，使用固定新合成库 `aic_v70_receipt_opt`，未清理旧库。覆盖 4 并发同标识仅一个案件 / 回执 / 原始版本、摘要冲突、撤权 / 只读、回滚后原标识重试、非目标外键异常和删案保留回执。
- PG 测试首次直接 ORM 建表因缺少 `vector` 扩展失败，DDL 事务回滚；修正为项目真实 Alembic 初始化后通过，失败日志一并保留。此为测试初始化修正，不是业务保存失败或删库重试。

## 可解释开销与建议

- 优化后每次带标识新增，SQL 从旧路径的 51 条变为 53 条，仅新增回执认领和绑定各一条；SELECT 数保持 33。不能为了基准删除唯一键、摘要或当前权限保护。
- 原编辑路径始终为 48 条 SQL，没有幂等标识或回执写入；观察到的编辑尾部差异不是多执行了回执逻辑。
- 三组新增的游标耗时中位数约 1.13–1.20 ms，而接口中位数约 23–24 ms。仅凭这些记录不能把余下耗时全部归于数据库或某个函数；如后续固定负载仍超标，再补细分追踪，不先做无依据的大改。
- 下一阶段应在目标服务器固定代表性负载下确认 P95 与事务提交 / 调度成本；不以开发机分位数波动继续扩大当前重构范围。
