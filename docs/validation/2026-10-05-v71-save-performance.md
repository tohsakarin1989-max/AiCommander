**2026-10-08 发布决定：** 用户明确回复“接受例外并发布”，接受最终严格编辑 P95 25.107→27.165ms（+8.20%、+2.058ms）作为本次 v7.5.0-stable 统一交付的单版例外，并授权提交/推送/Release。该决定不改变上述测试失败结论、原 5% 阈值及后续版本要求，不作为目标服务器性能验收。以下记录保持测量当时原貌。

## 冻结协议

- 基线为 Git 暂存区的 `7.0.0-stable` 工作包。一次读取 `backend/app` 与 `VERSION` 的 stage-0 文件清单，再以不可变 blob 对象只读导出，不创建 Git tree、提交或修改暂存区。
- 候选为运行开始时当前 `backend/app` 的完整冻结副本。两份源码、索引对象清单及两个测量脚本均归档；测量期间不读取变化中的业务源码。
- 复用 [v7.0 保存性能协议](2026-09-30-v70-save-performance.md) 的实际授权 ASGI、全新合成文件 SQLite、200 条种子案件、10 次预热与 50 个正式样本；两组各三轮，所有 150 个正式样本参与各操作的汇总。
- 固定执行顺序：第 1 轮基线→候选，第 2 轮候选→基线，第 3 轮基线→候选。不挑最佳轮、不删除失败或长尾样本，不调整垃圾回收。
- 两边 POST 均使用每次全新的 `Idempotency-Key`，必须产生新的自动编号案件，不用重复请求代替新增速度。
- 基线编辑使用旧 `PUT /api/cases/{id}`；候选使用强制来源版本核验的 `PUT /api/cases/{id}/edit-snapshot`。编辑前分别 GET 普通案件详情或一致编辑快照；准备 GET 不计入保存延迟和保存 SQL 数。该结果不是“打开编辑页面到保存”的完整用户等待时间。
- 保存计时包含认证、当前授权、路由校验、业务事务、写入审计及响应序列化；不含应用启动、建库、种子、登录和准备 GET。
- 每轮核验 260 个案件及独立编号、120 份原始修订、120 个分析 Outbox 事件、60 份提交回执。发现审计锁缺陷后补充两组相同的计时外检查：60 条新增审计、60 条编辑审计均须持久化；负载、计时范围、顺序和门槛不变。游标计时仅是归因辅助，不包含提交、文件同步和 Python 成本。
- 既定门槛保持为候选新增和编辑的汇总 P95 相对基线退化均不超过 5%；任何一个超标即退出码 1。P95 为排序后第 `ceil(n × 0.95)` 个值。
- 禁止网络、外部模型和现用数据库。结果仅是同机串行合成接口性能，不等同 PostgreSQL 性能、员工端体验、目标服务器或正式业务验收。

原始目录：`output/v71/case-save-performance/run-e_mn36ph/`。

新增 `test_case_edit_audit_v71.py` 使用独立文件 SQLite、真实 `AuthMiddleware`、真实 `get_db` 会话生命周期。修复前重现“PUT 200 但审计为 0 条”，修复后验证成功编辑及 409 冲突均有审计，原始修订 / Outbox 不重复。连同草稿、编辑并发与 v7.0 提交回归：**46 passed，6.39 秒**。

## 锁修复后归因与后续最小精简

- 新增路径两组 150 个正式样本全部是 **53 条 SQL**：33 SELECT、14 INSERT、3 UPDATE，以及 BEGIN / SAVEPOINT / RELEASE 各 1 条。新增中位数基本持平，不能把 P95 的 +23.16% 归因于额外数据库查询。
- 编辑从旧 **48 条**变为严格路径 **57 条 SQL**：增加 7 SELECT 与 2 个显式 BEGIN。其中锁内核验来源版本增加 1 次 SELECT，提交后的完整一致快照再读取案件、版本及四类明细增加 6 次 SELECT。两次显式事务分别保证 SQLite 写入准备与响应读取快照。
- 编辑汇总中位数增加 **3.744 ms / 16.85%**，各候选轮也高于邻近基线，存在需处理的固定开销信号，不能全部解释成偶发尾部波动。
- 游标耗时中位数：新增基线 / 候选为 1.024 / 0.946 ms；编辑为 1.037 / 1.052 ms。这一观察器不测提交、文件同步、ORM 物化、授权表达式构造和响应序列化，不能把完整编辑差值全部归于 SQL 执行。
- 本轮未进行运行时细分追踪，不能断言候选末轮长尾一定来自 GC、调度或某个函数。下一步如获授权，应先定位严格编辑重复读取 / 物化成本及共同长尾来源，在保持版本一致、权限和审计的前提下评估最小优化；不能靠继续跑到通过。
