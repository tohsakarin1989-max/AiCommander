# v4.0 查询接口与后台领取

当前发布基线仍为 v3.6.0-stable；接口已接入代码，但默认关闭，尚未完成普通用户页面与真实模型验收。

## 已接通

- `POST /api/intelligent-queries`：创建数据库待办，201及Location，不调用模型或Redis。
- `GET /api/intelligent-queries/{id}`：所有者查询，重新校验当前读取权限，成功响应no-store。
- `POST /api/intelligent-queries/{id}/cancel`：所有者取消，晚到完成不覆盖取消。
- 严格请求字段、UUID参数、身份认证、账号角色、四项未完成任务容量限制；异常不回显内部错误。
- 复用 ENABLE_AGENT_LAB 与 AGENT_MODE 开关；默认关闭。当前允许管理员及分析员，不绕过只读账号的既有写请求限制。
- Celery每5秒在AGENT_REDIS_QUEUE领取数据库待办，队列消息不携带问题或结果。
- Worker每次以任务所属账号重新读取权限，停用或撤权任务取消；遗留运行超120秒转过期。
- Worker配置125秒软期限、135秒硬期限；默认prefork环境的实际强制终止仍需演练，不能视为本轮已验证。

## 验证

- 接口5项测试通过，包括真实AuthMiddleware登录、匿名拒绝及Cookie来源限制。
- 后台领取4项测试通过，包括数据库待办领取、关闭开关、账号停用和模拟Worker重启后的过期清理。
- 全后端902项通过、1项跳过，用时35秒。跳过项要求独立PostGIS测试数据库，不计为通过。
- 差异检查通过；无生产数据迁移，未修改当前模型配置或发布GitHub。

模型为测试替身；直接调用Worker业务函数不等于真实Redis/Celery集成演练。
本轮证明提交路径不调用broker，实际断连恢复、硬期限、并发领取仍需真实进程验证。

后续真实进程证据：2026-09-10[队列恢复演练](v4.0-query-queue-recovery.md)已验证
Redis真正停止后待办仍保存、恢复后执行及两进程重复唤醒不重复领取。
原文的断连/并发待验状态由该记录取代；Beat、进程硬期限与强杀回收仍待验证。
后续同入口硬超时演练已补齐查询Beat、135秒实际终止和遗留过期回收，
详见该记录“实际硬期限与Beat回收通过”；原文待验描述为历史状态。
