# AiCommander 全项目业务链与逻辑审查：6.x 升级依据

日期：2026-09-27。审查对象：当前 `v5.4.0-stable` 工作区，包含尚未提交的业务精简、兼容迁移和语义整改。路线图见 [6.x 详细升级路线图](../superpowers/specs/2026-09-27-v6x-upgrade-roadmap.md)。

## 一、结论

**不宜继续按页面增加功能，也不需要重写整个系统。当前最重要的重构是统一分析来源、当前成果和人工确认对象，再深化案件过程理解。**

已具备离线地图、真实路由、自动画像、统一历史检索、受控多步助手、冻结成果、持续专题和设施档案。主要矛盾是新能力与旧即时分析并行：同一案件可能使用多套画像、两类候选来源、两种经验确认对象，不同页面选择不同结果。

建议从原五阶段草案调整为六节点：**6.0 主链归一 → 6.1 对象与历史条件 → 6.2 过程理解与助手 → 6.3 条件与道路研判 → 6.4 变化续算与性能 → 6.5 实务材料与区域关注。** 首版新增的是必要的业务整合阶段，不是新增一个 Agent 或管理页面。

### 证据边界

- 本轮是当前源码、路由消费者、持久化对象及已有验证材料的静态链路审查；覆盖主要业务链与保留功能，不宣称逐行安全审计或所有功能实机验收。
- 未启动实际业务环境、访问业务数据库、调用模型、修改业务实现、迁移数据、提交或发布。
- 上轮语义整改与前轮回归作为已有证据引用，本轮未将其重跑或计为新验收。
- 下述性能问题依据循环、全库读取和重复调用结构确认，**没有虚构目标服务器耗时**；源码存在功能不等于现场已启用。
- 独立地图、条件组和历史巡逻中仍保留其他算法；不能因部分评分接口已退役就声称所有旧风险分已清除。

## 二、业务链覆盖与取舍

| 业务链 | 当前能力与应保留部分 | 6.x 重构方向 |
|---|---|---|
| 登录、角色、厂区范围 | 请求绑定授权、ORM 范围过滤、成果读取再鉴权 | 统一来源/成果/后台任务的显式授权上下文，不重建用户系统 |
| 案件录入、Excel 导入、预检 | 导入批次与幂等、主要保存入口已有事务 Outbox | 补齐线索变更契约，消除保存后同步派生扫描 |
| 证据、人员车辆、回收、线索 | 独立事实记录与原文 | 保留来源类别与核实状态，不把举报线索直接当事实 |
| 预处理、画像、即时摘要 | 冻结画像与旧 `features` 并行 | 标准画像为当前入口，旧产物显式历史兼容 |
| 历史案例与经验检索 | 全部授权历史、极性、版本、pgvector | 索引化候选召回，缺索引后台补齐，完整查询可续跑 |
| 案件候选与道路 | v3.4 主成果和 v5.2 道路附件各有链路 | 发布同一成果组合，各候选类别有最低证据门槛 |
| 地图导入、离线显示 | 来源、模板、快照、包校验、发布与回滚 | 跨来源身份、有效时间、统一更新依赖；不重复制图 |
| 设施、区域、技防摘要 | 明确关联/邻近/候选分开，资料缺失明确 | 授权只读投影、关系索引、数据库聚合；补入口治理 |
| 旧辖区评价 | 仍有自动读取的旧风险上下文 | 停止新生成无充分依据的分数，保留历史版本 |
| 专题、条件组、图谱 | 专题冻结条件；旧图谱另做关联 | 一专题多视图；证据来源图谱保留独有用途 |
| 助手与 Agent 运行 | 已有真实 8 步工具循环、取消、条件继承 | 新业务工具、两类问答模式；日常能力与实验开关分离 |
| 经验卡、待办、确认 | JSON 历史卡与版本资产分别有确认状态 | 精确到版本的状态解析，不双向同步不同内容 |
| 报告、会议、周期材料 | 多类冻结/历史成果和导出 | 统一目录与引用，不强改历史内容类型 |
| 日常工作、大屏、事件 | 工作台已只读、事件为独立来源 | 统一统计范围、完整度与故障状态；原始事件保留 |
| 历史巡逻、模拟展示、管理员重放 | 历史与特殊入口仍有价值 | 只留兼容/高级/展示，不进入日常必经流程 |
| 调度、健康、恢复 | Outbox、租约、补偿轮询、独立健康与恢复文档 | 来源依赖、版本生效状态、业务能力健康；不造通用工作流平台 |

## 三、需要优先解决的实际问题

优先级指重构顺序，不代表已发现安全漏洞或现场故障。P1 为业务口径/有效性，应在 v6.0 处理；P2 为能力与扩展性，按依赖分期实施。

### A01 / P1：同案多套画像、聚合和即时分析

- `frontend/src/pages/Cases/Cases.tsx:643` 同时读取旧 automation、profile、processing-card、diagram；`:650` 又读 workspace；`:1876` 展示冻结成果，`:1900` 展示旧自动化复盘。
- `case_processing_card_service.py:19` 重新调用 profile；`case_automation_service.py:801` 组装完整模型上下文，`:808` 再生成经验预览。
- `case_profile_service.py:77` 优先显示旧 `features.summary`，没有标准画像同等的来源版本约束；`preprocess_service.py:399` 仍合并旧提取结果。
- 现有正确底座：`case_pipeline_service.py:311` 保存版本化画像，`case_result_service.py:148` 检查新原文与旧成果的时效。

**影响：** 阅读一个案件仍重复计算，旧摘要和新成果可能混看。**重构：** workspace 成为只读主契约；旧 API 转适配层，管理员重建走同一管线。不是再造第四种画像。

### A02 / P1：主成果与道路候选分属不同发布链

- `case_insight_service.py:410` 仍调用 `DualDomainV34`；`case_result_snapshot.py:58` 冻结这些候选。
- `case_result_service.py:86` 冻结后才触发道路任务；`case_facility_comparison.py:12` 已实现真正的设施召回、入口核验、道路批算和排序。
- `case_road_artifact_service.py:35` 道路结果独立存储；前端 `CaseRoadComparison.tsx:61` 明确两类结果不合并排名。
- `scorers/dual_domain_v34.py:106` 附近的囤储候选仍以聚落/仓储邻近作为主要启发，不能升级成新的有证据结论。

**影响：** 页面、报告、助手可能引用不同主候选。**重构：** 扩展当前成果快照的组合引用与选择策略，保留原附件；道路未完成显示部分/等待，不无提示回退为旧排名。仅有村屯邻近时停止生成新囤储候选。完整新评分放 v6.3，口径纠正不拖到该版本。

### A03 / P1：仍有日常消费者使用旧风险逻辑

- `Jurisdiction/Jurisdiction.tsx:317` 选案自动读取 risk-context、similar-targets、experience-card、roundtable-briefing。
- `jurisdiction_service.py:590` 仍按近案数、临路、未找到技防/巡逻点加分；缺资料被描述为覆盖不足。
- `gang_analysis_service.py:423` 以案数乘常量和时间跨度计算风险；`Gangs/GangAnalysis.tsx:157` 展示综合风险。

**影响：** 同一设施在新档案为未知，旧视图却表现为高风险。**重构：** 停止上述新分数；辖区页回归资料治理，旧条件组转专题视图。历史分数保留算法标记；历史巡逻没有因此被授权删除或恢复为新执行平台。

### A04 / P1：线索与人工解释未完整进入来源变更链

- `api/cases.py:1599` 保存 CaseTip 后提交并刷新质量，没有投递标准画像事件。
- `case_profile_service.py:168` 已显示线索台账；`case_pipeline_service.py:25、461` 的相关字段和源哈希未包含 tips。
- `case_intelligence_service.py` 的人工标签仍独立存于 features；不能直接把全部 features 加回原文提取。

**影响：** 补录线索可以看见，却未必影响画像与后续分析。**重构：** 明确原始事实、未核实线索、人工解释三类来源及版本事件；分别决定能用于什么推理，不增设逐字段审批。

### A05 / P1：旧链条推断既影响保存耗时，又缺更新失效

- `case_service.py:179、359` 创建/修改提交后仍同步刷新链条；`api/cases.py:1219` 坐标补录另行扫描。
- `chain_analysis_service.py:73、137` 基于角色、时间、直线距离形成候选；`:183` 已有关系直接返回，不刷新原距离与理由。

**影响：** 改时间/位置后旧推断可能保留旧依据；案件保存还等待额外扫描。**重构：** 首版迁为幂等后台消费者，候选绑定双方源版本并过期；人工确认关系保留，不自动撤销，附来源变化提示。后续统一条件候选，不能自动串并案。

### A06 / P1：经验确认状态仍有双来源消费

- `case_knowledge_service.py:62` 修改旧 JSON 卡；`knowledge_asset_service.py:305` 另行确认版本卡。
- 当前高级界面确认版本卡，但 `case_profile_service.py:59`、`case_processing_card_service.py:57` 和 `api/suggestions.py:244` 仍消费旧卡状态。

**影响：** 确认新版本后旧待办可能仍提示未确认。**重构：** 共用经验状态解析器，明确当前资产 ID、版本和审核记录；不能通过同步两个不同内容的确认状态掩盖问题。上轮“不继承旧确认、不覆写历史”修复必须保留。

### A07 / P1：部分统计由截断清单或错误零值推导

- `Reports/Reports.tsx:47、118` 获取有限会议列表后统计完成会议和案件次数；重复案件直接相加并非去重案件总量。
- `Events/EventCenter.tsx:51、158` 读取最多 100 条清单，统计缺失时回退列表长度或零值；共享时间/辖区仍有未应用边界提示。

**重构：** 后端明确范围、周期、去重口径和完整度；区分总量、展示条数和分析次数。故障显示不可用，保留独立事件来源关系，不将已有提示文字删除后冒充筛选已接通。

### A08 / P2：设施只实现来源内身份，历史适用时间尚待统一

- `map_foundation_service.py:523` 以同来源 canonical_key 认定身份，`:694` 身份包含 source_key；当前防同名误合并是正确行为。
- `:604` 版本有效期默认入库时间；生产有效期另在属性中，不能直接等同。

**重构：** 在稳定设施 ID 上增加可撤销的跨来源对应与有效时间，保留 claims 和旧 ID。案发时有效与当时系统已知分开查询；无历史资料不倒填当前值。

### A09 / P2：已有语义片段，但过程关系与模型结果尚未贯通计算

- `case_event_fragments.py:91` 明确句内共现；`case_semantic_service.py:23` 为固定词项字典。
- `case_pipeline_service.py:272` 将模型提取放独立候选层；`case_history_retrieval.py:52` 主要使用规则条件；模型结果不会自然改变排名。

**重构：** 形成带关系出处的过程条件 schema，区分原文陈述、提取候选、推断与正式确认；通过结构/来源/时空一致性校验的白名单派生条件才能进入比较。接通模型不是本功能完成的替代证据。

### A10 / P2：全库检索与设施读取成本随资料规模增长

- `case_history_retrieval.py:199、240、283` 在 5 秒预算内按 ID 扫描授权案例，缺有效索引时请求内补规则提取；已有 complete/partial 标记，不是假全库，但扫描顺序可能影响被比较集合。
- `facility_dossier_content.py:356` 打开单井仍读取窗口内案件并验证画像；`facility_condition_comparison.py:345` 分页设施仍遍历全部案件/事件和有效画像。
- `facility_summary_service.py:1、52` 当前摘要只维护设施目录，不是全部关联结果缓存。

**重构：** 数据库索引召回与聚合、候选证据加载、可重建关系索引、带授权版本的只读投影；结构、词项与向量独立召回后融合，不能以词项硬前筛丢失纯语义案例。完整长查询后台续跑。不能用最近 N 条截断来冒充性能优化或把敏感摘要放全域公共缓存。

### A11 / P2：助手已有多步能力，但工具与专题条件未覆盖完整业务

- `intelligent_query_loop.py:23、65` 已有九类工具及 8 步/120 秒动态循环。
- `intelligent_query_tools.py:236` 道路工具仅读现有附件，不发起新计算；设施档案与历史有效条件尚非独立工具。
- `topic_query_bridge.py:5` 正确拒绝不能表达的专用条件；`analysis_topic_service.py:197` 只支持标题/备注/暂停修订，没有条件版本和滚动窗口模型。

**重构：** 先扩展可精确表达的工具/条件契约，再开放相应专题；区分解释冻结结果与补查当前资料。不能丢掉道路限制后声称保存了同一个问题。

### A12 / P2：刷新机制已有，但缺贯通的依赖与变化解释

- `offline_map_service.py:399、1043` 有网格触发及固定外扩；与 50 公里候选召回、道路连通影响范围并不等价。
- `case_insight_service.py:321` 已有补偿，`road_refresh_jobs.py:32` 已有保守刷新，不能描述为永久不更新。
- `tasks/celery_app.py:27` 多类定时任务并存；版本变化与等待原因分布于多个状态对象。

**重构：** 共用依赖清单与业务就绪状态，不合并所有 Worker；事件合并、版本栅栏、差异解释和保守补偿协作。新增道路捷径也必须纳入影响范围。

### A13 / P2：成果入口分散，材料组织没有统一出口

- `Reports/Reports.tsx:47` 主要聚会议和案件成果；专题、查询、周期简报、经验复用快照各有入口。
- 各成果有不同业务来源，历史会议不能强转为案件结果。

**重构：** 只读成果目录 + 类型化引用 + 材料组装，统一查找和导出依据，不造第七种分析模型。证据图谱保留，作为来源展开；跨案模式图则成为专题视图。

### A14 / P2：日常智能能力仍与实验开关、运维口径耦合

- `api/intelligent_queries.py:36` 用 `ENABLE_AGENT_LAB/AGENT_MODE` 同时控制创建、读取和取消。
- `intelligent_query_worker.py:15` 依赖同一开关；`agent_observability_service.py:45` 总览排除智能查询和展示任务。

**重构：** 业务能力注册/健康投影，区分停止新任务、保留历史读取、取消在途任务；日常助手与实验区开关分离。复用现有运行表和权限，不引入第二套 Harness 或庞大调度平台。

## 四、必须保留与不重复立项

保留：原始案件、独立事件及转案件来源、人员车辆和证据、油品回收、正式人工关系、历史会议、版本报告、确认/归档经验、证据图谱、稳定深链接与必要管理员重放。

不重复建设：离线地图、Valhalla、pgvector、Outbox、冻结成果、多步助手、专题快照、语义否定分层。这些是已有能力，6.x 要改变业务连接方式、有效性和可用范围。

不建设：多 Agent 辩论、人人必填的复核流程、新巡逻/执法执行平台、通用资产主库、第二套路由/向量/图数据库。没有代码依据的重写不列入路线图。

建议先完成 v6.0 的 A01—A07 与 A14 开关边界，再实施智能深化；不能把消除错误旧口径推迟到系列末版。
